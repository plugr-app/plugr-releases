4. **Known bridge limitation:** the device bridge cannot delete files (`rm` fails with "Operation not permitted"). To delete, `mv` into a `_to_delete/` folder inside the repo and tell Josh so he can empty it. **Git corollary:** every git op that takes a lock leaves the lock file behind. Mitigate: (a) prefix ALL read-only git commands with `GIT_OPTIONAL_LOCKS=0` (env var; stops `git status`/`diff` from creating index.lock at all); (b) after any commit, immediately `mv` the leftover `.git/*.lock` + `.git/objects/*/tmp_obj_*` into `_to_delete/` — a stale `index.lock` blocks all future git commands including Josh's.
5. The mounted folder and any cloud sandbox are **separate filesystems**. Work on Josh's files through the mount. Use the cloud sandbox only for scratch work, and never assume a file written in one place exists in the other.

**If this session does NOT have the plugr folder connected:** say so immediately, in one sentence, and ask Josh to start a new task with the folder attached. Do not improvise a patch-script workflow. Do not write code against stale copies.

## 1. What Plugr is

A native macOS app for music producers, built by **Josh Isaacs** (call him Josh, not Joshua). Scans every plugin (VST3 / VST2 / AU / AAX / CLAP) and `/Applications` app, organizes them, checks for updates, tracks which plugins he actually uses across Ableton / Logic / FL projects, surfaces plugin deals, watches for sales on wishlisted plugins, and includes Tools (tap tempo, BPM↔delay, Camelot wheel) and Companion Apps (launchers for Native Access, Waves Central, etc.) tabs.

**Tech:** Electron 31 + React 18 + Vite. Universal binary (Apple Silicon + Intel). macOS 12+. macOS-only.

**Pricing:** $7/mo, $49/yr, $149 lifetime — all tiers 3 Macs, all features. 14-day trial caps update checks at 100 plugins and gates bulk ops, themes, iCloud sync, library export, backup/restore. LemonSqueezy is the license backend. Dev builds (`app.isPackaged === false`) bypass all entitlement gates — deliberate, don't "fix" it.

## 6. CRITICAL conventions that will bite you

### 6a. New top-level cache field = THREE places
1. `electron/lib/cache.cjs` → `saveCache()` schema serializes it.
2. `electron/main.cjs` → `patchCache()` preserve-list includes it (or it gets wiped on partial writes).
3. `electron/main.cjs` → `ALLOWED_PREF_KEYS` if user-settable via `prefs:set`.
This bug has shipped at least 4 times. Grep both lists every time.

### 6b. IPC naming
Main: `ipcMain.handle('namespace:verb', …)` → Preload: `pluginHub.namespaceVerb` → Renderer: `await window.pluginHub.namespaceVerb(…)`. The preload is the contract; grep it first when an IPC seems missing.

### 6c. Format families
Update-source additions propagate across a plugin's formats via `familyKeyFor()` + `applyRegistryAdditions()` in `src/App.jsx` (NOT an electron lib). Propagated items get `registryAppliedViaSibling: true` — they show the source but hide Edit/Remove (edit on the owning plugin). Touch anything cross-format → read those two functions first.

### 6d. Developer matching order
`developerByName` forced override → `userOverrides[id].developer` → bundle-ID `identifierPrefix` → alias → raw metadata. Never widen an `identifierPrefix` below two segments (`com.foo.` good; `com.f` caused the Trackspacer/W.A. Production bug).

### 6e. Cache schema changes require a `CACHE_VERSION` bump + migration.

### 6f. Duplicates semantics (post-1.0.19 — current law)
- **Family grouping: version-suffix vs model-number is decided by MAJOR-VERSION MATCH (2026-07-13, supersedes the digit-count heuristic):** `normalizeName(name, version)` in duplicates.cjs strips a trailing " V?<1-2 digits>" ONLY when the number equals `semver.coerce(version).major`. Neutron 3 (v3.x) → "neutron" groups with Neutron 4; RC 48 (v1.4.11) stays "rc 48" distinct from RC 24; SEM V2 (v2.13.2) groups with SEM V3; Pre V76 (v1.8.1) stays distinct from Pre 1973. Unknown version → keep the number. Trailing bare " V" (ARP 2600 V) always strips.
- **Same-version duplicate flags require matching bundle FILENAMES (2026-07-13):** true duplicates (same product, system + user dir) share a filename; companion variants registering the same friendly AU name from different bundles (Polyverse Gatekeeper.component vs GatekeeperMIDI.component) don't and are NOT flagged. Superseded detection ignores filenames (they change across versions).
- **"Not the same plugin? Unlink" (2026-07-13):** per-item `notDuplicate` override — applyOverrides strips `item.duplicate`; link on the cleanup card, Undo line in DetailPanel; in both benign-fields lists; main.cjs collapses falsy values. Escape hatch for product-line reboots (iZotope Trash v1.x vs Trash 2 v2.x — grouped but new product LOSES on version number; unfixable heuristically).
- **Multi-plugin shells are named honestly (2026-07-13):** an AU bundle with ≥ `SHELL_COMPONENT_THRESHOLD` (5) components keeps its on-disk bundle name — Waves WaveShell registers EVERY owned plugin as components of one bundle and used to masquerade as its alphabetically-first component ("Abbey Road Chambers (m)"), colliding across V15/V16 shells and hiding that trashing it kills every Waves plugin of that generation. FabFilter-style 2-3 component bundles keep the friendly component name.
- **Symlink/alias bundle copies collapse at scan (2026-07-13):** scanLibrary's dedupe pass resolves realpaths — installer-dropped symlinks (OpenVPN Connect) no longer produce self-duplicates; the real path wins; symlinks to targets outside scan roots survive as sole representative (external-drive workflows).
- **Packed AU versions (2026-07-12 fix):** `decodePackedAuVersion()` in plistParser.cjs — Arturia writes Apple's packed AU integer (0x10801 = 67585 = 1.8.1) into AU plist version fields, which displayed as "v67585" and read as "Newer than registry". Decoded for `.component` bundles only, in readBundleInfo + pluginWatcher. Guards: pure digits, ≥ 0x10000, major 1-99.
- **Plist version sanitation (1.0.22):** `saneVersion()` in `plistParser.cjs` — a version must START with a digit (optional "v" prefix); digit-containing is not enough (KORG AAX ships literal `KLAAXWRAPPER_M1_VERSION_STRING` placeholders, and semver.coerce extracts the "1" from "M1"). Applied in readBundleInfo (version, buildVersion, legacy AU components) and pluginWatcher. Unknown-version copies are NEVER marked superseded in duplicates.cjs (can't prove "older"), but still participate in same-format duplicate detection.
- Same plugin in multiple FORMATS = normal, never a duplicate.
- `duplicate` = 2+ copies at same version AND same format (largest size kept).
- `superseded` (OLD badge) = older version within the SAME format only. Cross-format version lag is handled by the updates system + the format-lag "Mark as current" acknowledgment, NOT by duplicates.
- Mono/Stereo (any letter-only parenthetical) variants are distinct groups.

### 6f-bis. Developer-level update sources (added 2026-10-20)
`developers.<Dev>.updateUrl` + `versionRegex` act as a **fallback** in `lookupRegistry` when the matched productMatcher has no source of its own. Product-level ALWAYS wins; absent fields change nothing. The resolved entry carries `registrySourceLevel: 'developer' | 'product' | null` for diagnosis.
**Only add one to a vendor whose entire catalog shares ONE version train.** The qualifying test (run against Josh's cache): that vendor's already-working plugins all check against a single URL, AND installed versions across its items are near-uniform, AND its regex is not product-specific. **Refinement (2026-10-20c):** "one working URL" was only ever a PROXY for the real criterion, which is **one version train**. ### 6f-quater. Legacy majors: the question is WHICH PRODUCT the page is about (rewritten 2026-10-22)
The original version of this section said: a matcher keyed to an old major that points at the current product page inherits the new major's number, so strip the regex and keep the link. **That was over-broad and Josh corrected it.** `UpdateBadge` already detects `latestMajor >= installedMajor + 1` and renders a **"Major upgrade"** chip whose tooltip reads "usually a paid upgrade rather than a free patch", and the row menu already offers **"Ignore this version" / "Ignore all updates"**. A user who owns RX 11 *wants* to know RX 12 exists. Demoting those sources threw away information the UI presents correctly.
**The real test is not "is the major different" but "is the page about the product the user owns".** Three situations, three answers:
1. **The page publishes the user's OWN version line → keep the regex.** Best case. FabFilter's "Legacy plug-ins" table keeps each previous major *maintained* — `Pro-Q 3.29`, `Pro-Q 2.30`, `Pro-C 2.22`, `Pro-L 1.37`, `Pro-R 1.20`, `Timeless 2.41`, `Saturn 1.31`, `Twin 2.41`, all dated Apr 16 2026 — so a Pro-C **2.22** owner reads `current` instead of being nudged to buy Pro-C 3. Regex shape: `<Name>\s+(<major>\.\d+)\s+[A-Z][a-z]{2}\s+\d{1,2},\s+\d{4}` (the date anchor is what keeps it out of the nav menu and the bundle-contents lists).
2. **The page publishes the SAME product's newer major → keep the regex.** The chip and the ignore actions are the designed handling. Applies to iZotope RX 11 → 12.1.0 (56 items), `Arturia / Mini V3` → Mini V4, `Arturia / Wurli V2` → Wurli V3.
3. **The page is about a DIFFERENT product → link-only.** This is the only genuine trap, because the number is not an upgrade of anything the user owns: `Plugin Alliance / SPL Vitalizer MK2-T` (PA 301-redirects the slug to **Vitalizer MK3-T**), `Plugin Alliance / elysia alpha mix` (the only page left is alpha **compressor** V2), `Arturia / MiniFreak V` (reports 5.1.0.**5869** against an installed 4.0.2.**6366** — the version rises while the BUILD falls, so it is the hardware editor, not the plugin), `NI / Kontakt 5` (the KSP manual's history tracks Kontakt 8).
**Three corollaries.** (0) **Demote the key that ACTUALLY matched, not the one that looks right.** For an app, the scanner passes the bundle name (`Avid Link.app`), not the cleaned display name (`Link`), so the vendor-prefixed key wins and a bare key added alongside it never fires — I demoted `Avid / Link` and `reFX / Cloud` and the bad regex on `Avid Link` / `reFX Cloud` kept running. The cache tells you which key won: `item.registry.matchedProduct`. Read it before editing. (1) Keep the bare vendor-word key source-less — `Saturn` and `Pro-Q` carry no URL on purpose so a Saturn 1 or Pro-Q 1 install cannot inherit the current line's number; only version-qualified keys get sources. (2) **Always follow redirects and compare the final slug to the requested one.** A 200 after a redirect is not confirmation.
**Two of my own claims here were wrong; both are corrected above.** "The support page's newest Pro-C 2 is 2.15, older than the installed 2.22" was read out of a *bundle-contents* listing further down the page rather than the Legacy table, which says 2.22. And "Blue Cat 3.5/4.5 is a legacy-major situation" was wrong — `BC Chorus 4` 4.5 → 4.6 and `BC Flanger 3` 3.5 → 3.6 are honest same-major updates.

### 6f-quinquies. Not every gap is a registry gap (observed 2026-10-21)
About 28 of the remaining no-source items are not products at all: uninstallers (`Uninstall`, `Uninstaller`, `REW Uninstaller`, `Kilohearts Slate Uninstall`), DAW/format shells (`AAX Shell`, `AU Shell`, `VST3 Shell`, `AvidAudioServer`, `DigiTest`), command-line and helper binaries (`Commandline`, `c4dpy`, `Logi Options+ Driver Installer`, `Genuine Software Integrity Service`), ARA companions (`AcousticaARA`, `Synthesizer V Studio 2 ARA Plugin`), updater/connect shims (`TracklibConnect`, `Musio Connect`, `BackblazeRestore`) and the Chrome-generated Workspace PWA shims (`Docs`, `Sheets`, `Slides`, `Chat`, `Copper`, `Password Manager` — their 132.0 / 8059.80 are shim versions, not app versions). **BUILT 2026-10-22 (Josh approved).** Registry-level, two routes:

### 6f-sexies. The INSTALLED version can be the broken half (added 2026-10-22)
§6f-quater is about a wrong number on the vendor's page. This is its mirror: the number in the **plugin's own Info.plist** is sometimes not the product's version at all, and comparing it produces a confident wrong verdict from a perfectly good source.
**The case that exposed it:** every `com.arturia.aax.*` bundle reports **1.4.6** — the AAX wrapper's version — across all **76** Arturia products, while the VST3/AU/VST copies of the same plugins report the real one and read `current`. That single string produced **55 false `outdated` and 20 false `ahead`**. Proof it is a placeholder and not a real version: all 76 are `format: AAX`, and **no** Arturia product reports 1.4.6 as its only version.
**Mechanism now in the code:** `placeholderVersions` on a developer or product entry (unioned, surfaced by `lookupRegistry` regardless of which level the source came from). `updateChecker.isNonInformativeVersion()` also catches **all-zero** versions (`0`, `0.0`, `0.0.0`) — Focusrite's `Red 2 EQ` and `Red 3 Compressor` report `0.0.0`, which means the scanner found nothing, not that they are ancient. Either case returns **`unknown`** with the fetched `latestVersion` still attached, so the user sees what the vendor publishes and compares by hand. Measured before shipping: **77 items move off a wrong verdict (57 `outdated` + 20 `ahead`), and 0 items lose a working `current` check.**
**Before declaring a placeholder, run the Arturia test:** the string must be shared across many distinct products of that vendor AND no product of that vendor may report it as its only version. A vendor-wide version that is genuinely real (Kilohearts' 2.4.6 on all 43 products, Softube's 2.6.40 on 406 items) looks identical on the first half of that test and would be destroyed by declaring it — the second half is what separates them.
**The test is a guard, not a gate.** Its job is to stop you destroying a version that is genuinely real: a vendor-wide string like Kilohearts' 2.4.6 (all 43 products) or Softube's 2.6.40 (406 items) passes the "shared across many products" half and would be wrecked by a careless declaration — the "no product reports it as its only version" half is what separates those from a placeholder. A single-item case can still qualify on different evidence, namely that the string is **impossible** as a version of that product: `Image-Line / FL Studio`'s AU copy reports `1.5.0` and its VSTi `1.0.0` against an FL that has been on major 20+ for years, so there is nothing real to destroy. Declare on impossibility OR on the Arturia test — never on a hunch.

### 6i. macOS compatibility is a DEADLINE, not a yes/no (rewritten 2026-10-22)
Josh: *"is this really a useful feature? Not sure it's working right? Or am I just really good at only having compatible software installed?"* — Compatible 4,489 / May not work 0 / Unknown 5.
**It was working, and that was the problem.** On Apple Silicon with a current macOS the "won't load" set is close to empty **by construction**: the only two ways in are a bundle declaring a newer minimum macOS than you run (essentially never) or one with no x86_64 slice at all. Josh's 57 files carrying a 32-bit `i386` slice all carry `x86_64` too, so they pass. That row reads 0 for nearly every user, which makes a correct feature look broken.
**The useful fact was in the data and being discarded.** `applyOsCompat` already detected Intel-only bundles and even tagged them `note: 'rosetta'` — then filed them under `status: 'ok'`. On Josh's library that is **176 files / 115 products** (Absynth 5, Iris 2, BreakTweaker, DDLY, Helm, BIAS AMP, M-Tron MkII, 8BitShaper, Focusrite Red 2/Red 3…). A natively-running arm64 host does not run those slowly — **it does not list them at all**.
**Timeline that makes this worth building rather than obsolete** (checked 2026-10-22, Josh raised the objection): macOS 26.4 began warning about Rosetta-dependent apps, **macOS 27 is the last release with full Rosetta 2 translation, and macOS 28 (2027) removes it.** Josh is on 27.0.1. So these do not degrade — they stop. The feature's value peaks over exactly the next 12–18 months, which is Plugr's launch window.
**Implementation:** a third `osCompat.status`, **`'rosetta'`**, distinct from `ok`. `applyOsCompat` flips the SAME bundle to `incompatible` (reason `rosetta-removed`) once `currentSystemVersion >= 28.0`, so the "Won't load" row is dormant rather than dead — it fills up the moment a user crosses that line, with no new detection needed. Buckets renamed **Native / Stops working on macOS 28 / Won't load / Unknown**, zero rows hidden, hover hints like the update buckets. Card, list pill and detail panel all surface it in **amber** (`--warn`, the "update available" colour) rather than the red reserved for "will not load" — it is a deadline, not a failure.
**Verified across the version boundary before shipping** with a 7-case table at macOS 27.0.1 / 28.0 / 28.1: universal→ok, x86_64-only→rosetta then incompatible, arm64-only→ok, i386+x86_64→rosetta then incompatible, i386-only→incompatible always, no-arch→unknown, min-29.0→incompatible always. **Post-rescan prediction for Josh: All 4,462 · Won't load 0 (hidden) · Stops working on macOS 28 **176** (115 products) · Native 4,277 · Unknown 9.**

### 6g. Update-source data model
- Bundled registry sources: `item.registry.updateUrl` + `versionRegex` (from `developerRegistry.json`).
- User-added sources: `userRegistryAdditions`, keyed by `item.identifier || item.id`, saved via `api.saveRegistryAddition(key, addition | null)` (null = delete). Marked `registryAddedByUser`; propagate to siblings (`registryAppliedViaSibling`).
- Mirror links: `overrides[childId].mirrorFromId` — child borrows parent's update status via `effectiveUpdates` in App.jsx.
- Sparkle: `item.sparkleFeedUrl`, most reliable when present.
- DiscoverModal phases: `chooser | searching | found | notfound | manual | saving | saved | sharing | error`; edit mode = `mode:'edit'` + `existingAddition` jumps straight to `found` prefilled.

### 6h-pre. Renderer data pipeline (order matters — deep-reviewed 2026-07-12)
`library.items` (raw from scan) → `applyRegistryAdditions(items, registryAdditions)` (merges user sources + sibling propagation) → `applyOverrides(items, overrides)` (favorite/hidden/developer/category/subcategory/extraCategories/notes/tags/mirrorFromId → flags like `developerOverridden`) → `displayedItems` → `matchesFilters`/`filteredItems` (reads `effectiveUpdates`, not raw `updates`). `effectiveUpdates` deliberately reads mirror links from `overrides` directly because it runs BEFORE applyOverrides in the memo graph. ~75 IPC channels; the preload exposes ~100 methods. Update-source fix flows: DiscoverModal `deriveSourceFromVersion` (`updates:deriveFromVersion`) builds a regex from a user-typed version; `updates:tryTemplate` applies a found source pattern across siblings; `updates:applySharedSource` applies a shared-dev-page URL verbatim to siblings.

### Original spec / design rationale

Motivation: shipping bundled categories (see 2026-07-16(g): 538-entry supplement) fixes the *known* uncategorized plugins, but new/obscure plugins will keep landing at "Undefined" on users' machines. This spec closes that long tail without per-user manual work, while keeping the SHARED registry clean. **Core principle: the curated registry is the source of truth; AI only fills it faster; Josh's review gates anything that reaches the shared registry.** Three tiers, Josh's review is the constant.

**Tier 1 — Gap-reporting → Josh categorizes (default, opt-in).** Plugr sends back ONLY the uncategorized `{productName, developer}` pairs from a user's library — never library contents, paths, or anything else (same privacy bar as the existing community consent copy; opt-in). These aggregate into a queue weighted by how many users share each gap (most common "Undefined" plugins float up). Josh then runs the exact 2026-07-16(g) process — Claude pre-categorizes from knowledge + web research, confidence-rates each, Josh approves — and the results append to `tools/category-seed-supplement.json` → `npm run seed-categories` → ships in the registry next release. Reuse: this is the SAME review pipeline as §15 (community update-source review); a category submission is just another entry type in that queue, not a second system to maintain. Automation ceiling: shrink Josh's effort to reviewing only the low-confidence flags (a scheduled task pulls new gaps, Claude categorizes + flags uncertain ones, Josh glances at ~10%). Unanimous high-confidence ones *could* eventually auto-apply, but keep the human gate until the pipeline is proven.

**Tier 2 — Self-serve AI-assist (fallback for users who don't opt into Tier 1).** A "Categorize my undefined plugins" action generates a copy-paste prompt pre-loaded with Plugr's EXACT category vocabulary (Instrument: Synth/Sampler/Drums/Keys/Bass/Guitar/Orchestral/Generator; Effect: EQ/Dynamics/Reverb/Delay/Modulation/Distortion/Pitch/Imaging/Utility/Creative/Multi-Effect; MIDI; Application) + the user's uncategorized list. User pastes it into their own AI (ChatGPT/Claude/etc.), pastes the answer back; Plugr VALIDATES every returned category/subcategory against the taxonomy (reject invalid), then applies as local `userOverrides` immediately — instant win, no registry involvement. Optional "also submit these" → routes into Josh's Tier-1 review queue, NEVER straight to the shared registry (LLM hallucination must not pollute everyone).

**Tier 3 — Manual per-plugin edit** — already exists (DetailPanel category edit → `userOverrides`).

**Data model / reuse notes:** categories piggyback on the community pipeline — extend the additions entry (or a sibling `categoryAdditions` array in `additions.json`) with `{ key, pluginName, developer, category, subcategory }`; `applyCommunityAdditions` already merges registry fields, so add category/subcategory there. Validation on import must enforce the taxonomy (pull the valid set from `categorize.cjs`). Privacy: only name+developer+category ever leave the machine, opt-in, no library contents. Never auto-publish AI output to the shared registry.
